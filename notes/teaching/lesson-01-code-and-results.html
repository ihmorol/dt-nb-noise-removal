Lesson 01 — What the new code does, and what the results say

Mission: understand your own project well enough to defend every table to Prof. Farid without notes. Read this once now, once the night before the meeting. Ask the agent anything that is still fuzzy.

1. The story in five sentences

Your submitted paper describes an experiment but its results table was empty. The experiment could not simply be "run", because the paper promises the 2014 study's own tools (Weka's J48 tree + a textbook Naive Bayes on the original data columns), and the combined algorithm only existed in a different toolbox (scikit-learn). So we built the missing experiment in the promised toolbox, ran it honestly, and the paper's hybrids lost ~5 points to a plain tree. Then we searched for a strategy that removes noise without that damage, using mathematics to choose the design: a committee of three different judges voting on each row. It wins, significantly.

2. The code

2.1 The two toolboxes ("worlds")

The repo already had two separate implementations:

  • Pipeline world (main.py): sklearn's CART tree, one-hot columns, its own NB. Like cooking the recipe with whatever pans you own.
  • Replication world (replicate_farid.py): the paper's own tools — Weka J48 (which is C4.5), a hand-built textbook NB (FaithfulNB), original columns. Like sourcing the exact brand of ingredients the original chef used.

The manuscript promises the second kitchen. The combined algorithm existed only in the first. Filling the table with first-kitchen numbers would contradict the paper's own Methods section.

2.2 e9_farid.py — the experiment engine

One script tests 12 "recipes" (arms) side by side on identical data splits:

Arm (plain words)What it does
no cleaning → NB / → treebaselines: how good is the data as-is?
Algorithm 1 → treeNB deletes rows it misclassifies, then a tree learns (Farid's Alg 1)
Algorithm 2 → NBa tree picks useful columns and weights them, then NB learns (Farid's Alg 2)
chain instances→attrs, chain attrs→instancesthe paper's Algorithm 3: run both steps in sequence, each order
parallelboth steps work independently on the same data; keep surviving rows × surviving columns
two reference armsone step each, ending in the "other" classifier — for attribution

Each arm is evaluated with 10-fold cross-validation, repeated with 10 different shuffles (seeds): cut the data into 10 pieces, let each piece take one turn as the exam while the other 9 teach. 100 exams per arm per dataset. Nothing is judged on data it has seen.

Protocol B (used for all headline numbers) is the honest exam: before each quiz, the cleaning is redone using only that quiz's training material — the cleaning never peeks at the exam students. Protocol A (also reported) cleans once using the whole dataset, exam students included — like grading yourself after deleting the questions you got wrong. We run A only to show how high a score cheating reaches.

Efficiency trick: one J48 run answers several questions at once — its accuracy is the C4.5 row, its tree structure is Algorithm 2's column choice, and the same tree starts the attributes-first chain. About 5–6 Java calls per fold instead of ~10.

Reading Weka's answer sheet: Weka prints a confusion matrix — a grid, rows = true class, columns = predicted class. From one grid we compute both accuracy (diagonal ÷ total) and macro-F1 (average of per-class F1). A built-in guard demands the grid's accuracy match Weka's own printed summary, else the program stops — this caught one real parsing bug during development.

Deletion diary: every deletion is logged per class — how many rows of each class were removed, and what share of that class that is. Not "we expelled 30 students" but "30, of which 25 were music students".

New data files: results/EXP-E9_farid/versions/<dataset>/parallel.csv holds the parallel-cleaned dataset (original columns) plus a removals.txt explaining every removal. Inspection only — it was cleaned with full-data knowledge, so it is not evaluation data.

2.3 e5_strategy.py — the strategy search

Three judges, three thinking styles, all fitted on training data only:

  • NB — the probabilist: judges by frequency counts.
  • J48 tree — the checklist writer: judges by if-then rules.
  • Standardized logistic regression — the border drawer: judges by a sliding score. (sklearn, not Weka — see the caveat in §4.)

Their mistakes are different mistakes — measured: on glass, NB is wrong on 47% of rows, the tree on 7%. That difference is the whole engine of the strategy.

Four treatments of a suspected-noise row:

TreatmentRuleAnalogy
hard (Farid's)delete if the NB judge misclassifies itexpel every student one teacher flunks
softkeep all, vote weight = judge's confidence in the row's labelsuspect students stay, but count as 0.2 of a vote
correctrelabel only if ≥2 of 3 judges agree on the same different answerretake: two of three teachers must agree on the new answer
committeedelete only if ≥2 of 3 judges misclassify itexpulsion needs a majority of the panel

Fractional counts (faithful_nb.py): NB can now learn from "30.5 students' worth" of evidence — implemented without touching the old code path, so every previous number still reproduces exactly (verify_faithful.py still passes: ALL PASS).

2.4 The honesty machinery

Pre-registration (DECISIONS.md). Every formula, threshold, judge and success criterion was written and dated before the runs. Like sealing your prediction in an envelope before results day — nobody can say you picked rules that fit the answers.
Determinism anchors. Before trusting the new engine, it had to reproduce the old committed numbers exactly (breast-cancer, 3 seeds: 75.31 / 72.39 / 71.61 / 72.63 — identical to the decimal). Like proving the new oven bakes the old recipe identically before trusting it with a new one.
Documented mechanics fixes: the loader breaks on pandas 3 (pinned pandas<3); Weka's Logistic cannot converge on NSL-KDD's huge-valued features (two 600-second timeouts — it fits unscaled features, so ridge 1.0 is still ~zero regularization there), so the third judge became sklearn's standardized logistic — same thinking style, different implementation, changed because of the crash, before any results were analyzed.

3. The results

3.1 Experiment E9f — the paper's Table II (honest retest, 10 datasets × 10 seeds)

MethodAccuracyMacro-F1
No cleaning → tree (C4.5)86.3381.92
Algorithm 1 (filter → tree)81.0375.70

chain instances→attrs → tree81.2175.76

No cleaning → NB75.9369.80
  • The implementation is trustworthy: baselines land within ~3 points of the 2014 paper (C4.5 +2.81, NB −1.40) — so when the hybrids fail, it is not our code.
  • Every filter method loses ~5 points to the plain tree. Deleting "noise" deletes the hardest — and usually correctly-labelled — rows.
  • The leak story: cleaning before cross-validation inflates every filter method by +13.5 to +16.5 points. The 2014 numbers live exactly in that inflated range — their protocol was underspecified, and under the honest protocol the gains vanish.
  • Order does not matter (p=0.92 and p=0.28 for the two chains).

3.2 Experiment E3b — parallel cleaning

Parallel 81.05, chain-1 81.21, chain-2 80.89 — a statistical three-way tie. So the "interaction" between the two algorithms (each seeing the other's output) buys nothing. The damage comes from the row deletion itself, wherever it runs. Bonus: the design {none, single, sequential, parallel} is now complete.

3.3 Experiment E5 — the strategy that wins

committee delete85.77+4.74, p=0.0078−0.11 median, p=0.65 (a tie)

Headline: committee deletion and committee correction both beat Farid's hard deletion significantly (p < 0.01), and committee deletion is statistically indistinguishable from not cleaning — you now remove noise and pay nothing for it.

Why it works (measured, not claimed): on NSL-KDD hard deletion removes 7,374 training rows per fold; the committee removes 293 — because there the tree errs on 0.2% and logistic on 1.4% of rows, so NB's false "noise!" verdicts get outvoted. On glass: 91 deletions become 42. A false expulsion now needs two independent mistakes to coincide — probability ~e², not e (the Condorcet jury effect; Brodley & Friedl 1999 measured the same).

Why soft weighting failed (an honest negative with a mechanism): NB posteriors saturate — it is nearly always ~0% or ~100% sure. Its low-weight rows turned out to be almost the same rows hard deletion removes (e.g. 414 vs 413 per fold on image segmentation). Weighting through an overconfident judge is not actually "soft". The lever is the diversity of judges, not continuous weights.

Where the committee beats even no cleaning: diabetes +2.03, plus iris, vote, glass. Where it loses: tic-tac-toe (−5.6) — the one dataset where all three judges err heavily together. The honest claim for the paper: never-worse-except-where-judges-fail, better-where-noise-is-real, significantly-better-than-the-original-filter.

5. Glossary (plain words)

fold / 10-fold CV
cut data into 10 parts; each part takes one turn as the exam, the rest teach.
seed
the shuffle number. 10 seeds = 10 different exam schedules, so no lucky split decides the grade.
protocol A / B
B = clean inside each fold (honest). A = clean once on everything first (leaky; shown for contrast).
arm
one recipe in the comparison (e.g. "filter rows, then grow a tree").
confusion matrix
Weka's grid: rows = true class, columns = predicted class. Accuracy and macro-F1 both come from it.
macro-F1
average of per-class F1 scores, so a huge class cannot hide a failed small class.
judge
a model that flags training rows it thinks are mislabelled. Farid's judge is NB.
posterior / confidence weight
the judge's probability that the row's existing label is right.
Wilcoxon test
a paired significance test over the 10 dataset-level scores; p < 0.05 = the difference is unlikely to be luck.
pre-registration
writing the plan (and the success criteria) before seeing results.
